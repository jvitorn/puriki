# Releasing Puriki for Android

This document holds the reusable release-engineering rules for Puriki. It is
the permanent successor to the temporary `PURIKI_ANDROID_RELEASE_PLAN.md`,
which has been removed now that Feature 1.0 is complete and its useful
history has been migrated here.

## Release invariants

- The Android package is `com.jvitorn.puriki`.
- Public releases use semantic versions in `app.json`.
- Every new Android APK must use an `android.versionCode` greater than every
  APK previously released with the same package.
- Puriki 1.0 uses `version: 1.0.0` and `android.versionCode: 1`.
- Choose the next patch, minor, or major version from the actual release
  scope. Version and versionCode increments are manual.
- All APK variants produced from one release (see Multi-ABI packaging below)
  share the same `version`/`versionCode`. Puriki does not publish to Google
  Play, so there is no need for per-ABI versionCode math.
- Keep the same production signing key for every upgrade. Never commit a
  keystore, `credentials.json`, passwords, or private signing material.

## Production configuration

The EAS profile is `production-apk`:

- environment: `production`
- distribution: `internal`
- development client: disabled
- Android build type: `apk`
- version auto-increment: disabled

The EAS `production` environment supplies these public OAuth identifiers:

- `EXPO_PUBLIC_ANILIST_CLIENT_ID`
- `EXPO_PUBLIC_MAL_CLIENT_ID`

Do not configure client secrets as `EXPO_PUBLIC_*` values. EAS-managed Android
credentials must continue using the established production key.

## Multi-ABI packaging

Puriki ships one direct APK download through GitHub Releases rather than a
single Google Play AAB, so a single Gradle/EAS build produces one APK per
supported ABI plus a universal fallback, instead of one oversized universal
APK.

This is implemented as a small, persistent Expo Config Plugin —
`plugins/withAndroidAbiSplits.js` — registered in `app.json`'s `plugins`
array. Because Puriki uses Expo prebuild/CNG and does not commit the
generated `android/` directory, the plugin re-applies this configuration to
`android/app/build.gradle` on every prebuild via `withAppBuildGradle`. It is
idempotent (detects its own marker comment and skips re-insertion) and fails
loudly instead of silently doing nothing if the expected `android {` anchor
ever disappears from the Expo/React Native Gradle template.

The plugin injects:

```groovy
splits {
    abi {
        enable true
        reset()
        include "armeabi-v7a", "arm64-v8a", "x86", "x86_64"
        universalApk true
    }
}
```

All four ABIs are included because they already match the project's default
`reactNativeArchitectures` (`android/gradle.properties`, regenerated by every
prebuild) and no native dependency in the project — including the local
`modules/purikuki-translation` module and its Google ML Kit Translate
dependency — excludes any of them. `universalApk true` keeps a
maximum-compatibility fallback APK alongside the per-ABI ones.

A single `eas build --platform android --profile production-apk` (or a local
`cd android && ./gradlew assembleRelease`) therefore produces every APK
variant from one build. Outputs land in
`android/app/build/outputs/apk/release/`. `eas.json`'s `production-apk`
profile sets:

- `android.applicationArchivePath` to the universal APK, so EAS always has an
  unambiguous single "primary" artifact.
- `android.buildArtifactPaths` to `android/app/build/outputs/apk/release/*.apk`,
  so every generated APK (all ABI-specific variants and the universal one) is
  collected and downloadable from the EAS build results page, not just the
  primary one.

Do not run a separate EAS build per ABI — that defeats the purpose of this
configuration and wastes build minutes.

## Preflight

```bash
npm ci
npm run typecheck
npm run lint
npm run format:check
npm run test:ci
npx expo-doctor
npx expo config --type public
npx eas-cli@latest config --platform android --profile production-apk
```

Verify the intended `version`, increasing `android.versionCode`, package,
production environment, APK build type, and disabled development client
before starting a build.

## Build and accept the APKs

Run a production build only when a new artifact is actually required:

```bash
npx eas-cli@latest build --platform android --profile production-apk
```

Download every APK the build produced (see Multi-ABI packaging above — expect
one `arm64-v8a`, one `armeabi-v7a`, one `x86_64`, one `x86`, and one
`universal` APK). Install at least the universal APK, and ideally the
`arm64-v8a` one too, on real Android devices and validate the full acceptance
checklist below. Confirm the app runs without Metro, a development client, or
a development menu.

### AniList and MyAnimeList OAuth verification checklist

AniList's OAuth flow previously regressed in a production APK while
continuing to work in the native Developer Build; MyAnimeList was unaffected.
Because AniList's implicit-grant redirect is controlled entirely by the
**Redirect URL** configured for the OAuth application on AniList's own
developer settings page (Puriki never sends a `redirect_uri` parameter — see
`src/infrastructure/auth/anilist/expo-anilist-oauth-client.ts`), a production
regression there is a provider/environment-configuration risk, not
necessarily an application bug. Before and after every production build,
confirm:

1. The `EXPO_PUBLIC_ANILIST_CLIENT_ID` and `EXPO_PUBLIC_MAL_CLIENT_ID` values
   configured in the EAS `production` environment are the intended ones (do
   not print the actual values in logs or documentation).
2. AniList's developer settings page shows a Redirect URL of exactly
   `puriki://auth/anilist` for that exact client ID (no trailing slash, no
   stale `exp://` value, no different path).
3. On the installed production APK: AniList sign-in opens the browser,
   completes authorization, returns to Puriki, validates OAuth `state`,
   persists the session, and loads the user's list.
4. MyAnimeList sign-in still works end-to-end (OAuth with PKCE, list loads).
5. Logout/reconnect works for both providers.

If AniList fails only in the production APK again, `src/infrastructure/auth/oauth-diagnostics.ts`
provides a production-safe diagnostic (active in release builds, never logs a
token/code/secret) — capture `adb logcat` filtered for `[OAuth] Callback
result` during a reproduction attempt. It reports provider, expected redirect
URI, the `WebBrowser` result type, the callback's scheme/host/path, whether
OAuth `state` matched, and a high-level failure category, which is enough to
tell a provider-redirect mismatch apart from a client-ID/configuration
problem or an application defect.

### Production APK acceptance checklist

On a real Android device, with the app installed as a production build (no
Metro, no dev client, no dev menu):

1. Clean install and/or upgrade over the previous signed build.
2. App launches; splash and startup transition complete normally.
3. Onboarding completes for a fresh install.
4. AniList-only, MyAnimeList-only, both-connected, and no-provider account
   states all behave correctly (see the OAuth checklist above for AniList).
5. Primary-provider switching works once both accounts are connected.
6. Catalog browsing (Home, Search) and list reads/writes work for both
   providers.
7. Add/remove list item, and progress/status/score mutations, all work,
   including rapid-multitap episode progress.
8. On-device synopsis translation works, including the first-time model
   download and recovery from a corrupted model.
9. Launcher icon (all adaptive-icon masks), splash, and bottom navigation
   render correctly.
10. App restart preserves persisted sessions and settings.
11. No debug UI, development menu, or crash is reachable in normal use.

## Prepare the release assets

Rename each accepted artifact using:

```text
puriki-v<version>-<abi>.apk
puriki-v<version>-universal.apk
```

For Puriki 1.0:

```text
puriki-v1.0.0-arm64-v8a.apk
puriki-v1.0.0-armeabi-v7a.apk
puriki-v1.0.0-x86_64.apk
puriki-v1.0.0-x86.apk
puriki-v1.0.0-universal.apk
```

Only publish the ABI variants that were actually generated and accepted;
never publish an artifact that was not the one tested. Recommended public
positioning:

- **Primary download:** `arm64-v8a` — covers virtually all modern Android
  phones and tablets at a fraction of the universal APK's size.
- **Compatibility:** `universal` — works on any supported device; the safe
  default for users unsure which to pick.
- **Older devices:** `armeabi-v7a`.
- **Emulators / x86 devices:** `x86_64`, `x86`.

Calculate SHA-256 for every published asset after the final rename:

```bash
sha256sum puriki-v1.0.0-arm64-v8a.apk puriki-v1.0.0-universal.apk # ...and so on
```

PowerShell:

```powershell
Get-FileHash .\puriki-v1.0.0-arm64-v8a.apk -Algorithm SHA256
```

Record every checksum in the GitHub Release notes. Do not calculate a
checksum from a different build or rename a file after recording it.

## Publish through GitHub Releases

1. Create the release tag `v<version>` from the accepted release commit.
2. Create a non-draft public GitHub Release for that tag.
3. Attach every accepted APK variant, each named per the convention above.
4. Include installation context (which file to pick), material changes,
   known limitations, and each asset's SHA-256 in the release notes.
5. Verify every asset downloads and installs over the previous release when
   applicable.
6. Refresh and deploy the official landing page so its stable-release
   metadata points to the new assets.

## Update policy

Puriki 1.0 is a set of standalone APKs. It does not require EAS Update, OTA
channels, `runtimeVersion` for OTA, an in-app version checker, automatic APK
downloads, or background update infrastructure. Users update manually by
installing a newer officially signed APK. Update infrastructure may be
evaluated for Puriki 2.x.

## Security notes

- No personal credentials, API secrets, or `.env` files are tracked in git.
  `.env` is correctly gitignored; only `.env.example` (empty placeholders) is
  committed.
- `EXPO_PUBLIC_MAL_CLIENT_SECRET` exists as an optional code path in
  `src/infrastructure/auth/mal/mal-auth-config.ts`, defaulting to an empty
  string and unused today. **Do not** set this as an EAS environment
  variable: any `EXPO_PUBLIC_*` variable is inlined into the JS bundle and is
  recoverable from the compiled APK, so it cannot hold a real secret. MAL's
  OAuth PKCE flow does not require a client secret for a public mobile
  client — leave it unset.
- All verbose auth diagnostics are gated behind `__DEV__` and are compiled
  out of release builds, except the intentionally production-safe OAuth
  callback diagnostic described above, which never logs a token, code, or
  secret by design.
- No localhost/dev-server URLs, mock providers, or test accounts are wired
  into production code paths.
